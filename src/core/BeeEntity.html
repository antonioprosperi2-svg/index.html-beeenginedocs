BeeEntity — Documentazione Tecnica

Classe madre base per tutte le entità di gioco in BeeEngine

📁Panoramica

BeeEntity è la classe fondamentale da cui derivano (o a cui si ispirano) tutti gli oggetti attivi di un gioco costruito con BeeEngine: il giocatore, i nemici, le piattaforme, i proiettili, i power-up. Gestisce quattro responsabilità core che quasi ogni entità di gioco 2D condivide:

1. Posizione e dimensioni (x, y, width, height) 2. Movimento tramite velocità (vx, vy) e gravità opzionale 3. Collisioni rettangolari (AABB) e risoluzione fisica delle collisioni solide 4. Gerarchia padre-figlio, per composizione di entità complesse (es. un nemico con un'arma agganciata)

Il design è deliberatamente "piatto" e senza dipendenze da un framework grafico specifico: BeeEntity non sa nulla di come viene disegnata (delega tutto a draw, che a sua volta può delegare a un engine.drawEntity), il che la rende riutilizzabile sia con "canvas" puro sia con altri sistemi di rendering.

📁Architettura interna

Stato di base

this.x = x; this.y = y; this.width = width; this.height = height; this.vx = 0; this.vy = 0; this.gravity = 0; this.isGrounded = false; this.active = true; this.visible = true; this.destroyed = false; this.collider = null; this.children = [];

📁Da notare tre coppie di flag booleani con significati distinti e volutamente separati:

active controlla se l'entità viene aggiornata (update)

visible controlla se viene disegnata (draw)

destroyed è un marcatore logico di "questa entità è morta", che però non rimuove l'oggetto dalla memoria né dagli array dei genitori — è responsabilità di chi gestisce la lista di entità (una scena, un pool) controllare questo flag e fare l'effettiva pulizia (es. filtrare l'array ad ogni frame o riciclare l'oggetto in un object pool).

Questa separazione è utile: puoi avere un'entità invisibile ma ancora attiva (es. un'area trigger invisibile), o disattivata ma ancora visibile per un frame di dissolvenza in uscita.

Gerarchia di entità (children)

addChild(entity) { this.children.push(entity); return entity; } removeChild(entity) { this.children = this.children.filter(child => child !== entity); }

Ogni BeeEntity può contenere altre entità figlie. Questo pattern (comune nei motori a scene graph) permette la composizione: ad esempio, un nemico può avere come figlio un'arma che si muove relativamente a lui, oppure il giocatore può avere come figlio un'aura o uno scudo temporaneo

update e draw propagano automaticamente la chiamata a tutti i figli attivi/visibili, quindi basta chiamare i due metodi sulla radice della gerarchia perché l'intero albero venga processato.

Da notare che le coordinate x/y dei figli in questa implementazione non sono relative al genitore — sono assolute, esattamente come per qualsiasi altra entità. La gerarchia qui serve per organizzare l'update/draw, non per un sistema di trasformazioni annidate in stile "parent-relative transform".

📁Collisione AABB (collidesWith)

collidesWith(other) { if (!other || other === this) return false; return ( this.x < other.x + other.width && this.x + this.width> other.x && this.y < other.y + other.height && this.y + this.height> other.y ); }

Questo è il classico test Axis-Aligned Bounding Box: due rettangoli si sovrappongono se e solo se si sovrappongono sia sull'asse X che sull'asse Y.

È il metodo di collision detection più economico in termini di calcolo (solo confronti numerici, nessuna radice quadrata o trigonometria) ed è la scelta giusta per la stragrande maggioranza dei giochi platform/arcade 2D dove le hitbox sono rettangoli non ruotati.

Da notare: il metodo usa direttamente this.x/y/width/height, non l'eventuale this.collider creato con addRectCollider.

Questo significa che se un'entità ha un collider con offset personalizzato (diverso dal bounding box grezzo dell'entità), collidesWith lo ignora — è un dettaglio importante da tenere presente: il collider dedicato esiste ma questo metodo non lo consulta automaticamente.

📁Risoluzione delle collisioni solide (resolvePlatformCollision)

Questo è il metodo più delicato della classe, e merita una lettura riga per riga perché implementa una tecnica classica ma con alcune scelte specifiche.

const overlapX = Math.min(this.x + this.width - platform.x, platform.x + platform.width - this.x); const overlapY = Math.min(this.y + this.height - platform.y, platform.y + platform.height - this.y); if (overlapY < overlapX) { // risolvi verticalmente } else { // risolvi orizzontalmente }

La logica calcola quanto le due entità si sovrappongono su ciascun asse, poi risolve la collisione lungo l'asse con la sovrapposizione minore.

L'intuizione: se la sovrapposizione verticale è più piccola di quella orizzontale, vuol dire che l'entità sta "toccando appena" la piattaforma dall'alto o dal basso, quindi ha senso spingerla fuori verticalmente (e viceversa per l'asse orizzontale)

Questa è una tecnica standard per collisioni discrete (non continue) tra rettangoli, ed è efficace nella maggior parte dei casi tipici di un platform, con il limite noto di tutte le collisioni discrete:

a velocità molto alte un'entità può "bucare" un ostacolo sottile tra un frame e l'altro (fenomeno noto come tunneling), perché il test avviene solo sulla posizione già aggiornata, senza controllare la traiettoria percorsa nel frame.

Il ramo verticale merita attenzione particolare:

if (this.vy >= 0 && this.y + this.height - this.vy * 0.1 <= platform.y + 10) { this.y=platform.y - this.height; this.vy=0; this.isGrounded=true; return true; } else if (this.vy < 0) { this.y=platform.y + platform.height; this.vy=0; }

La condizione this.vy >= 0 distingue "sto cadendo o sono fermo verticalmente" da "sto salendo" (vy < 0, tipicamente durante un salto). Se sto cadendo, l'entità viene "agganciata" sopra la piattaforma (platform.y - this.height) e marcata come isGrounded

Se invece sto salendo e collido, vengo respinto sotto la piattaforma (utile per simulare la testa che sbatte contro un blocco dal basso, come nei platform stile Mario).

Il controllo this.y + this.height - this.vy * 0.1 <= platform.y + 10 è una tolleranza euristica: invece di verificare la posizione esatta del bordo inferiore dell'entità, sottrae una piccola frazione della velocità verticale (vy * 0.1) e aggiunge un margine fisso di 10 pixel alla soglia della piattaforma.

Questo crea un margine di tolleranza che rende l'atterraggio più "morbido" e meno sensibile a piccole discrepanze di frame-timing, evitando che l'entità venga respinta lateralmente per errore quando in realtà sta solo atterrando. È una soluzione pragmatica tipica dello sviluppo di platform game "a sensazione",

più che una formula fisicamente rigorosa — funziona bene nella pratica ma i valori 0.1 e 10 sono magic number che andrebbero probabilmente esposti come parametri configurabili se il comportamento di atterraggio necessita di essere ritoccato per generi diversi di gioco.

Il ramo orizzontale è più semplice: spinge l'entità fuori dal lato da cui proviene, basandosi sul segno di vx.

📁Il ciclo update

update(dt, input, engine) { if (this.gravity > 0 && !this.isGrounded) { this.vy += this.gravity * dt; } this.x += this.vx * dt; this.y += this.vy * dt; this.isGrounded = false; for (const child of this.children) { if (child.active && child.update) { child.update(dt, input, engine); } } }

Il pattern è quello classico basato su delta-time (dt): la velocità viene applicata proporzionalmente al tempo trascorso dall'ultimo frame, non a un numero fisso di pixel per frame — questo garantisce che il gioco si comporti in modo consistente indipendentemente dal framerate del dispositivo.

Un dettaglio cruciale da non perdere: this.isGrounded = false viene eseguito ad ogni frame, prima del controllo delle collisioni con le piattaforme. Questo significa che il flag va "riconfermato" ogni frame chiamando resolvePlatformCollision

per ciascuna piattaforma rilevante dopo aver chiamato update — se il codice della scena dimentica di richiamare resolvePlatformCollision dopo update,

l'entità risulterà erroneamente "in aria" anche se è ferma su un terreno solido. È un'interazione tra metodi che chi integra la classe deve conoscere: l'ordine delle chiamate nel game loop è significativo.

📁Disegno (draw)

draw(ctx, engine) { for (const child of this.children) { if (!child.visible || !child.draw) continue; if (engine && typeof engine.drawEntity === 'function') { engine.drawEntity(ctx, child); } else { child.draw(ctx, engine); } } }

Interessante notare che BeeEntity.draw() disegna solo i figli, non sé stessa. Questo implica che le classi derivate (es. una classe Player extends BeeEntity) devono fare l'override di draw() per disegnare il proprio sprite, chiamando eventualmente super.draw(ctx, engine)

per propagare comunque il disegno ai figli. È una scelta di design che separa "disegnare questa entità" da "disegnare l'albero sotto questa entità".

Il controllo su engine.drawEntity permette al motore di intercettare centralmente ogni chiamata di disegno (utile per applicare effetti globali, ordinamento per z-index, o batching), con fallback al metodo draw diretto dell'entità se l'engine non lo implementa.

📁Distruzione (destroy)

destroy() { this.active = false; this.visible = false; this.destroyed = true; }

Come accennato sopra, questo metodo non rimuove l'entità da nessuna struttura dati — si limita a marcarla. La rimozione effettiva (dall'array children del genitore, da un array di nemici in una scena, ecc.) è responsabilità del codice chiamante, che tipicamente controlla destroyed per filtrare le entità morte a fine frame.

📁Perché è scritto così — note per chi integra la classe

Estendere, non modificare. BeeEntity è pensata per essere sottoclassata (class Giocatore extends BeeEntity), sovrascrivendo update e draw e richiamando super.update()/super.draw() per non perdere il comportamento base (movimento, gravità, propagazione ai figli).

L'ordine update → resolvePlatformCollision non è intercambiabile. Come spiegato sopra, isGrounded viene resettato a false dentro update; se non richiami resolvePlatformCollision subito dopo per ogni piattaforma rilevante, il salto (che dipende da isGrounded) smetterà di funzionare correttamente.

collidesWith e resolvePlatformCollision vanno chiamati esplicitamente dalla scena, non avvengono automaticamente: BeeEntity non tiene una lista globale di "cosa può collidere con cosa" — è compito del codice di gioco decidere quali coppie di entità testare (es. giocatore contro ogni piattaforma, non ogni entità contro ogni altra, per motivi di performance).

I magic number nella risoluzione verticale (0.1, 10) sono tarati per un "feeling" di gioco arcade tipico; se un gioco richiede un comportamento di atterraggio più preciso o diverso (es. un gioco fisico più realistico), vale la pena esporli come parametri configurabili della classe piuttosto che valori fissi nel codice.

📁 Riepilogo API

Metodo Ritorna Scopo
addRectCollider(offsetX, offsetY, width, height) BeeRectCollider Crea e assegna un collider rettangolare con offset personalizzabile
addChild(entity) BeeEntity Aggiunge un'entità figlia alla gerarchia
removeChild(entity) void Rimuove un'entità figlia dalla gerarchia
collidesWith(other) boolean Test di sovrapposizione AABB tra due entità
resolvePlatformCollision(platform) boolean Risolve una collisione solida, spingendo l'entità fuori dalla piattaforma
update(dt, input, engine) void Applica gravità, movimento e propaga l'update ai figli
draw(ctx, engine) void Propaga il disegno ai figli (non disegna sé stessa)
destroy() void Marca l'entità come inattiva, invisibile e distrutta
